# ADR-0037: Usage rollups, the four KPIs and reports (Step 2.7)

Status: accepted. Completes what ADR-0029 left out ("Deliberately not included"). Changes none of D1-D15.

## Context

ADR-0029 shipped usage ingest (`POST /usage/events`), the per-asset summary (`asset_usage`), the dashboard overview and the unused-assets tracker. Step 2.7 still asks for: partitioned `usage_events` with nightly rollups (ClickHouse-free), the four BRD KPIs (publishing effort, duplicate reduction, reuse, workflow SLA attainment), per-asset analytics, storage by folder, a report API and scheduled email reports (MIS), and ingest of 1M events/day without API p95 above 500 ms. The spec does not define the KPIs, so this ADR does.

## Decisions

1. **`usage_events` is range-partitioned by month on `occurred_at`.** Primary key `(id, occurred_at)`. A scheduler job (`analytics.partitions`) keeps the current month and the next three present, and a default partition catches strays so an event is never lost (a month that strays landed in gets its own partition at the next run, and the strays are moved into it). When `DAM_USAGE_RETENTION_MONTHS` is above 0 the job detaches and drops whole months older than the **retention horizon** (the first day of the month that many months before the current one, so at least that many full months and the current one are always kept) **only after** every day of the month has been rolled up: a month with a day still marked for rollup is kept until the next run. 0 (default) keeps everything. Partitioning is mainly for cheap retention and bounded scans; ingest does not need it at 1M/day (about 12 events/s). The app roles cannot run DDL, so partitions are created and dropped by `SECURITY DEFINER` functions (`usage_events_ensure_partition`, `usage_events_drop_partition` and helpers) executable only by the system role the scheduler uses; the drop function itself refuses the previous month and anything newer. Every partition has forced RLS like every other tenant table.
2. **Dedupe moves to its own table.** A unique index cannot span partitions without the partition key, so `usage_event_keys (tenant_id, client_event_id)` (primary key) records every client event id. Ingest stays one statement: insert the keys `ON CONFLICT DO NOTHING RETURNING`, insert events only for the ids that were new (and for events without an id), bump `asset_usage` for those, and mark their days for rollup. Resending a batch is still a harmless `duplicate`; concurrent resends still cannot double count; a client id repeated inside one batch is stored once. Rows are written in key order so concurrent batches queue instead of deadlocking. With retention on, the job prunes keys recorded before the horizon; with retention off they stay.
3. **Rollups.** `usage_daily (tenant_id, day, asset_id, event_type, channel, uses)` holds one row per UTC day, asset, event type and channel (`channel` is `''` when unspecified, never null, so it can be part of the key). Ingest records `usage_rollup_dirty (tenant_id, day, mark_seq)` for every day an event lands on, bumping `mark_seq` from a sequence each time. The `analytics.rollup` job (every 10 minutes, and 02:15 UTC for a full re-check of the last 3 finished days of every tenant, marked or not) recomputes each dirty tenant-day in one transaction (advisory lock per tenant-day, delete the day's rows, insert from events, then delete the mark **only if `mark_seq` has not moved since it was read**), so back-dated batches and re-runs are idempotent, never double count, and an event that lands during a rollup keeps its day marked for the next run. Today is never rolled up. **Reads** (overview, top assets, per-asset analytics, the reuse KPI, reports): finished days that are not marked come from `usage_daily`; today and every marked day come from `usage_events`, combined in ONE statement (one snapshot), so the figures are exact whether or not the job has run, and identical before and after it. The unused-assets list reads `asset_usage` as before (it never read events), so it needed no change. With retention on, a day before the horizon whose month has been dropped is **sealed**: its raw events are gone, so the rollup leaves its `usage_daily` rows alone and just clears the mark; a late event for such a day is counted in `asset_usage` and then discarded with the other strays, but not added to the rollup.
4. **`assets.first_published_at`** (nullable) is set by the domain the first time an asset becomes `published` (in `Asset.ChangeStatus`, which every publish path goes through: a person, scheduled publish, a workflow's automatic publish), never cleared; the migration back-fills it from the audit trail's `asset.status.changed` rows (to = `published`, earliest). The back-fill reads `assets` and `audit_log`, which have forced RLS, so the migration must run as the database owner that is a superuser (as in the shipped stack); an owner that is not would back-fill nothing (new publishes are unaffected). It makes publishing effort a cheap query.
5. **The four KPIs** (`GET /analytics/kpis?days=30`, 1-365, UTC calendar days ending today, compared with the equal-length period before). Aggregates are computed in SQL; the median and 90th percentile use `percentile_cont` (linear interpolation between the closest ranks; `KpiMath.Percentile` writes the same rule down and is unit-tested):
   - **Publishing effort**: among live (non-deleted) assets whose `first_published_at` falls in the period (start inclusive, end exclusive), the median and 90th-percentile hours from `created_at` to `first_published_at` (never negative), and the first-pass rate: the share with **no workflow task rejected before the asset was first published** (an asset published without a workflow counts as first pass; a rejection of a later round, after the first publication, does not count against it). Lower hours and a higher first-pass rate are better.
   - **Duplicate reduction**: of the uploads created in the period that finished (status ingested or duplicate), how many were recognised as an existing file and not stored again (`duplicatesPrevented`), the rate (`prevented / uploads`), the bytes not stored (the duplicate upload's size), and `duplicateAssetsInLibrary` (live assets whose checksum another live asset shares, i.e. duplicates that were allowed through or predate the check). The latter is a snapshot; its "previous" figure is estimated from the assets created before the period (later deletions are not known).
   - **Reuse**: among live assets with at least one use in the period (`usedAssets`), how many were used at least twice (`reusedAssets`), the reuse rate (`reused / used`), the average uses per used asset, and `multiChannelAssets` (used on two or more channels; uses with no channel are not a channel). Computed from the rollup plus live events (decision 3).
   - **Workflow SLA attainment**: among workflow tasks that had a due time and were decided (approved or rejected) in the period, the share decided on or before it (`attainment`), plus `breached` (tasks whose SLA breach was recorded in the period) and `overdueOpen` (pending tasks past due right now; a snapshot, so null in the previous-period figures).
   Every KPI returns its previous-period value; a KPI with no data in the period returns `null` for its ratio (and for hours), never 0%.
6. **Report API.** `GET /analytics/reports` lists the reports; `GET /analytics/reports/{name}?days=&format=json|csv` runs one. Names: `kpis`, `top-assets`, `unused-assets`, `storage`, `workflow-sla`. A JSON report is `{name, title, generatedAt, period, columns[{key,label,type}], rows[], truncated}`; a row is an object keyed by column key (strings, numbers, null); column types are `text`, `count`, `number`, `percent` (a ratio from 0 to 1), `bytes`, `hours`, `datetime` (ISO 8601). In the `kpis` report percentages are shown as 0-100 with a `unit` column. `top-assets` lists up to 100 rows; `unused-assets` up to 5,000 (`days` is the idle window, up to 3650); `truncated` says there were more. `storage` lists folders (one row each with its direct assets and bytes and the totals of its subtree, parents before children, plus "(no folder)") and then asset types (largest first); `workflow-sla` has a row per workflow step. CSV (`format=csv`, content type `text/csv`) starts with a UTF-8 BOM, writes the column labels, neutralises formula-leading text cells with an apostrophe, quotes commas, quotes and line breaks, writes numbers plainly and percentages as "83.3%". Needs `analytics.read`; rows that name assets (`top-assets`, `unused-assets`) honour the caller's read scope exactly as the unused list does; the other reports are tenant-wide aggregates like the overview.
7. **Per-asset analytics**: `GET /analytics/assets/{id}?days=30` (needs `analytics.read` and read access to the asset; an asset the caller cannot read is a 404, indistinguishable from one that does not exist): uses in the period against the equal period before, uses ever, first/last use ever, a zero-filled daily series, uses by event type and by channel (20 busiest; no channel is `unspecified`), and the 20 most recent uses (actor id, type, channel, time).
8. **Scheduled reports (MIS).** `report_schedules` rows (report name, period days, frequency `daily|weekly|monthly`, hour UTC, weekday 1-7 (Monday = 1) or day of month 1-31 (a day beyond the end of a short month means its last day), recipients, enabled, last sent) are managed under `/analytics/report-schedules` with the new permission `analytics.manage` (Admin, Librarian); at most 50 per tenant, 50 recipients each; create, update and delete are audited (`report_schedule.created|updated|deleted`). The `analytics.reports` job (every 15 minutes) sends each due schedule through the existing email sender (ADR-0031), **building the email for each recipient from that recipient's own access** (a recipient without `analytics.read`, a disabled user, or one with no email address is skipped and the schedule says so; reports that name no asset are built once). A recipient is recorded on the schedule as soon as their email was accepted, so a failed send is retried at the next run for the others only, and neither a retry nor a restarted scheduler mails anyone twice for the same slot; a slot that could not be delivered 24 hours after it was due is given up (`lastError` says so) and the schedule moves to its next slot. **Recipients are users of the tenant** (ids, active, validated on every save), not arbitrary addresses, so a schedule cannot be used to mail outsiders. The email carries an HTML table of the first 50 rows, a count of the rest, and a link to the report in the console (`{DAM_CONSOLE_PUBLIC_URL}/insights/reports/{name}?days={days}`; no link when no public address is configured); CSV is downloaded from the console (the email port has no attachments). With no SMTP server configured nothing is sent and the schedule shows "Email is not configured on this server (set DAM_SMTP_HOST)." in `lastError`. `POST .../send-now` mails every recipient immediately without changing the schedule's place: 202 with `{sent, skipped, failed}`, or 409 when email is not configured or nothing could be sent.
9. **Ingest performance** is verified by an integration test (batches of 500 posted concurrently; p95 of the endpoint under 500 ms with the partitioned table and the key table) and by a repeatable script, `tools/perf/usage-ingest.mjs`; the measured results are below.

## Configuration

| Variable | Default | Meaning |
|---|---|---|
| `DAM_USAGE_RETENTION_MONTHS` | `0` | Scheduler. Above 0: usage events (and event keys) older than this many full months before the current one are dropped, a month at a time, after they were rolled up. 0 keeps everything. |
| `DAM_ANALYTICS_PARTITIONS_CRON` | `0 30 1 * * ?` | Scheduler. When partitions are created and retention applied (Quartz cron, UTC); also once shortly after start. |
| `DAM_ANALYTICS_ROLLUP_CRON` | `0 0/10 * * * ?` | Scheduler. How often changed days are rolled up. |
| `DAM_ANALYTICS_RECHECK_CRON` | `0 15 2 * * ?` | Scheduler. The full re-check of the last three finished days. |
| `DAM_ANALYTICS_REPORTS_CRON` | `0 0/15 * * * ?` | Scheduler. How often due scheduled reports are sent. |

Scheduled reports use the email settings of ADR-0031 (`DAM_SMTP_*`) and `DAM_CONSOLE_PUBLIC_URL` for the link. Time is UTC calendar days throughout, as in ADR-0029. The scheduler must be able to execute the maintenance functions, which the migration grants to the system role.

## Performance (measured)

Apple-silicon laptop, Postgres 16 in a Docker VM (the integration fixture), API in-process with pooled connections, 300 assets, batches of 500 events with unique client ids spread over 30 days and 11 channels:

| Run | Result |
|---|---|
| Integration test, 40 batches of 500 (20,000 events), 4 workers | about 21,000 events/s; per request p50 85-88 ms, p95 118-129 ms, p99 167-173 ms |
| Same, 8 workers (saturates the machine; all writers queue on the tenant's day rows and the hot assets) | about 16,000-18,000 events/s; p50 156-182 ms, p95 412-440 ms, p99 544-767 ms |
| `tools/perf/usage-ingest.mjs`, 100,000 events, concurrency 4, over a real socket | 4.69 s, 21,335 events/s (42.7 requests/s); p50 83.7 ms, p95 142.2 ms, p99 232.0 ms, max 308.2 ms; 0 failures |
| One request at a time | p50 53 ms, p95 64 ms (the single SQL statement is 30-45 ms of that) |

That is about 1.8 billion events/day at this rate against a target of 1 million. The integration test asserts p95 under 500 ms with 4 workers and under 1,500 ms with 8 (a guard against a lock convoy on a slow CI runner, not a promise). One tenant's writers serialise on that tenant's day and asset rows, which is the ceiling of a single tenant (about 20,000 events/s here); different tenants do not queue behind each other.

## Consequences

- One migration (`UsageRollupsAndReports`) converts `usage_events` to a partitioned table (rename the old one, create the partitioned one with the same columns, key and indexes, create a partition for every month from the oldest event to three months ahead, copy, record the keys and mark every event day, drop the old one, all in the migration's transaction), adds `usage_event_keys`, `usage_daily`, `usage_rollup_dirty`, `report_schedules`, `assets.first_published_at` and indexes for the KPI queries, with RLS and grants. A test runs it on a database that already holds events, and back down and up again. Down restores the single table and loses nothing.
- Three scheduler jobs: `analytics.partitions` (daily), `analytics.rollup` (10 minutes + nightly re-check), `analytics.reports` (15 minutes). The dashboard and every report read correctly even if none of them has run.
- A KPI is a definition, not a fact: this ADR is the place to change one, with a CHANGELOG note, because a changed definition breaks comparison with earlier periods.
- Built-in roles are re-synced from code at API start, so existing tenants get `analytics.manage` for Admin and Librarian on the next restart.
- Known limits: today's figures are aggregated from today's events on each request (about a million rows at the target volume; a few hundred milliseconds), which is the price of exactness without the job; storage is the size of each asset's current version (ADR-0029), not the object-store bill.

## Changes from the first draft of this ADR

The first draft left these open; the implementation settled them: the first-pass rule counts only rejections before the first publication; `ReportDto` gained `truncated`; the report rows and column types above; `duplicateAssetsInLibrary` and `overdueOpen` are snapshots (estimated or null for the previous period); reuse and publishing effort leave out deleted assets; send-now answers 202 with counts (409 when nothing could be sent); recipients' emails are built per recipient; a slot undelivered for 24 hours is given up; sealed days under retention; the console link path; the retention horizon and the maintenance functions.

## Console

- **Insights** (sidebar, needs `analytics.read`) has three pages joined by a row of links: Key results (`/insights/kpis`), Unused assets
  (`/insights/unused`, unchanged) and Reports (`/insights/reports`). The period (30, 90, 365 days or a custom 1-365) lives in `?days=` and is
  remembered per browser; it travels between Key results and Reports.
- **Key results** shows the four KPIs as cards: the headline figure, a "Better / Worse / No change" pill and the previous period's value (the
  direction that counts as better is stated in words, never by colour alone), the supporting figures from decision 5 and a "How this is measured"
  disclosure per card. A ratio with nothing to measure reads "No data yet" with the reason, never 0%.
- **Reports** previews a report (first 100 rows), downloads it as CSV through the authenticated client (as a blob, so the byte-order mark Excel
  needs for Hindi survives), and for `storage` draws the top-level folders as bars sized by their subtree bytes. A **Schedules** section (needs
  `analytics.manage`) lists, creates, edits, deletes and sends schedules; recipients are picked from tenant users.
- The link in a scheduled email, `/insights/reports/{name}?days=N`, is a console route that forwards to `/insights/reports?report={name}&days=N`.
- The asset page gets a **Usage** card (30 or 90 days: daily bars, first and last use, uses by kind and channel, the five latest uses), loaded only
  once the card is near the viewport.
- **Known limit:** the recipient picker lists users through `GET /users`, which needs `users.manage`. A Librarian holds `analytics.manage` but not
  `users.manage`, so for them the picker cannot search and recipients show as short ids. A lightweight tenant user directory (names only, any
  signed-in user) would fix this and the same limit in the workflow designer's assignee picker; it is not part of this step.
- `BarChart` (ui-kit) no longer labels a regular tick that sits closer than N bars to the always-labelled last bar, which made the last two date
  labels overlap on a 30-day chart.
